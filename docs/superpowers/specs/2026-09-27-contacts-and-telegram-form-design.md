# Спека: реальные контакты + отправка формы в Telegram

- **Дата:** 2026-09-27
- **Статус:** утверждён дизайн, готово к планированию
- **Связанные документы:** `PRODUCT.md`, `DESIGN.md`

## 1. Цель

Заменить черновые плейсхолдеры контактов и идентичности реальными данными и
сделать форму заявки рабочей: POST с фронтенда → PHP-обработчик → Telegram-бот →
сообщение в заданный чат. Токен бота хранится только на сервере.

Успех: посетитель может написать в один клик по любому каналу; отправка формы
доставляет структурированную заявку в Telegram и даёт понятную обратную связь;
при сбое путь к связи не теряется (fallback на прямые контакты).

## 2. Область

**Входит:**
- Реальные значения имени, контактов, соцсетей, ссылок CTA.
- Рабочая отправка формы через PHP в Telegram.
- Обновление `PRODUCT.md` (реальные контакты; бэкенд и отправка больше не «вне scope»).

**Не входит:**
- Метрики (47 проектов, «с 2019 года», «5 лет») и цены/сроки тарифов — остаются
  черновыми плейсхолдерами.
- Отправка заявок в MAX, аналитика, CMS, мультиязычность.
- Пункты критики P1 (перегруз 7 каналов, AA-контраст) — отдельная работа.
- Капча и защита от целевых атак (остаётся honeypot + сдержанный rate-limit).

## 4. Архитектура и поток данных

```
Браузер (index.html + js/app.js)
  │  POST send.php  (application/x-www-form-urlencoded)
  ▼
PHP send.php
  ├─ honeypot → тихий ok (без отправки)
  ├─ валидация name / contact
  ├─ rate-limit по IP
  ├─ cURL → https://api.telegram.org/bot{TOKEN}/sendMessage
  └─ JSON-ответ {ok, error?} + HTTP-код
  ▲
config.php (BOT_TOKEN, CHAT_ID, DRY_RUN, лимиты) — вне git, закрыт .htaccess
```

Прогрессивное улучшение: форма имеет `action="send.php" method="post"`, поэтому
работает и без JS (нативный POST, `send.php` отвечает простым HTML-подтверждением
при `Accept: text/html`, JSON — при fetch). При включённом JS отправка идёт через
`fetch` с состояниями и fallback.

## 5. Фронтенд

**Разметка формы** (в CTA-секции): поля `name`, `contact`, скрытый honeypot
`website` (невидим, `tabindex="-1"`, `autocomplete="off"`), кнопка submit.
Атрибуты: `action="send.php" method="post"`, `novalidate` (валидация своя).

**Клиентская валидация:** оба поля непустые; `name` 2–80 символов; `contact`
5–120 и похож на email (`@` и точка) или телефон (только цифры, пробелы, `+`,
`-`, `(`, `)`, `@`). Ошибки — инлайн рядом с полем, с `aria-describedby`.

**Состояния:**
- idle → «Отправить заявку →».
- loading → кнопка `disabled`, текст «Отправляем…».
- success → сообщение «Спасибо! Заявка отправлена — отвечу в течение дня.»
- error → «Не удалось отправить. Напишите напрямую: Telegram · MAX · Email»
  (прямые ссылки) + повтор доступен.

Контейнер сообщения: `role="status" aria-live="polite"` (уже есть). Фокус
переводится на сообщение при success/error. Тексты — на русском.

**Отправка:** `fetch('send.php', { method:'POST', headers:{'Accept':'application/json'}, body: new FormData(form) })` с таймаутом (например 10 с). Ошибка сети/таймаут/не-2xx → состояние error.

## 6. Backend `send.php`

**Контракт:** только `POST`. Ответ — JSON `{"ok":true}` либо
`{"ok":false,"error":"<machine-code>"}`. HTTP-коды: `200` успех/тихий honeypot,
`400` невалидные данные, `405` не POST, `429` превышен лимит, `500` сбой
Telegram/сервера. Для нативного POST (`Accept: text/html`) — минимальная HTML-
страница подтверждения/ошибки.

**Порядок обработки:**
1. `REQUEST_METHOD !== 'POST'` → `405`.
2. Honeypot `website` непусто → `200 {ok:true}` (не отправлять).
3. Нормализация и валидация полей (те же правила, что на клиенте, но источник
   истины — сервер). Невалидно → `400`.
4. Rate-limit по IP: не более `RATE_MAX` заявок за `RATE_WINDOW` секунд
   (по умолчанию 5 за 600 с). Превышено → `429`. Хранилище — файлы, имя = хэш IP;
   каталог — `sys_get_temp_dir()` по умолчанию, переопределяется константой
   `RATE_DIR` (при её объявлении в `config.php`).
5. Формирование текста: имя, контакт, время (UTC+5), IP, `User-Agent` (обрезанный).
6. cURL `sendMessage`: `chat_id`, `text`, `parse_mode=HTML`,
   `disable_web_page_preview=true`. Пользовательский ввод экранируется
   (`htmlspecialchars`) перед вставкой в HTML-разметку сообщения.
7. Разбор ответа Telegram: `ok:true` → `200 {ok:true}`; иначе → `500`.

**DRY_RUN:** если `DRY_RUN` включён, шаг 6 заменяется логированием и возвратом
`200 {ok:true}` без реального запроса (для локальной проверки).

## 7. Конфиг и секреты

`config.php` (создаётся на сервере, **не** коммитится):
```
const BOT_TOKEN = '123456:...';   // от @BotFather
const CHAT_ID   = '123456789';    // получатель
const DRY_RUN   = false;
const RATE_MAX    = 5;
const RATE_WINDOW = 600;
```
Рядом — `config.example.php` с плейсхолдерами (коммитится). `config.php` в
`.gitignore` и закрыт `.htaccess` (для Apache: `Require all denied` в отдельном
`.htaccess` рядом с файлом либо директива в корневом). Токен не логируется и
никогда не попадает в клиентский код или ответ.

## 8. Инструкция по настройке бота

1. В Telegram открыть `@BotFather` → `/newbot` → задать имя и username → получить **токен**.
2. Написать созданному боту любое сообщение (или добавить в нужный чат/группу).
3. Узнать `chat_id`: открыть `https://api.telegram.org/bot<TOKEN>/getUpdates` и
   взять `message.chat.id`, либо написать `@userinfobot`. Для группы id
   отрицательный; бота нужно сделать админом группы.
4. Создать `config.php` на сервере по образцу `config.example.php`, вставить
   `BOT_TOKEN` и `CHAT_ID`, при необходимости включить `DRY_RUN` на время проверки.
5. Отправить тестовую заявку с сайта и убедиться, что сообщение пришло.

## 9. Обработка ошибок и fallback

Любой сбой (сеть, 4xx/5xx, `send.php` недоступен, Telegram `ok:false`) → фронт
показывает состояние error с прямыми ссылками Telegram/MAX/email. Сервер никогда
не возвращает пользователю технические детали или токен — только machine-code.

## 10. Доступность

- Поля имеют `label` (текущий подход — визуально скрытый `sr-only` label + `placeholder`).
- Ошибки связаны с полями через `aria-describedby`; honeypot скрыт от AT.
- Сообщение статуса — `role="status" aria-live="polite"`, фокус переводится на
  него при завершении.
- Кнопка в состоянии loading остаётся фокусируемой и сообщает `aria-busy`.
- Контраст ошибок/успеха — не ниже AA (учесть правку P1 отдельно).

## 11. Тестирование

Автотестов нет (статический сайт без тест-инфраструктуры). Проверка:

1. **Локально:** `php -S localhost:8000` в корне проекта; в `config.php` включить
   `DRY_RUN`. Проверить: валидную отправку (`{ok:true}`), пустые/невалидные поля
   (`400`), honeypot (тихий `200`), GET (`405`), rate-limit (`429`).
2. **Контакты:** клики открывают `t.me/ArtKull`, `max.ru/…`, `mailto:`, `tel:`;
   VK/GitHub ведут на реальные профили; инициалы `АК`.
3. **UX/доступность:** состояния loading/success/error, `aria-live`, фокус,
   клавиатурная работа, `prefers-reduced-motion`.
4. **Боевая отправка:** после подстановки реального токена — одна тестовая
   заявка; проверка прихода сообщения в чат.

## 14. Риски и ограничения

- **Секрет на хостинге:** токен хранится в `config.php` в web-root (защищён
  `.htaccess`); при возможности вынести выше `public_html` — сделать (подход 1→2).
- **Спам:** honeypot и rate-limit сдержанные; при росте спама — добавить капчу/очередь.
- **Дубли заявок:** при двойном клике возможны две отправки — кнопка
  блокируется на время запроса.
- **php-окружение:** требуется PHP с расширениями `curl` (и `json`). Проверить на хостинге.
- **Логотип MAX:** бренд-ассет используется только как иконка ссылки; следить за
  актуальностью официального файла.
